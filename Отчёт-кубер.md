# Отчёт по развертыванию приложения MentorFlow в Kubernetes

## 1. Использованные абстракции Kubernetes
Для запуска приложения и его зависимостей в кластере Minikube были использованы следующие манифесты:

* **Deployment**: Обеспечивает декларативное управление подами. Было создано три деплоймента (для `mentorflow-app`, `postgres` и `redis`). Это гарантирует автоматический перезапуск контейнеров при сбоях и позволяет легко масштабировать приложение
* **Service (ClusterIP)**: Использован для баз данных `postgres-service` и `redis-service`. Выделяет стабильные внутренние IP-адреса, делая БД доступными исключительно внутри изолированной сети кластера
* **Service (NodePort)**: Использован для основного приложения `mentorflow-service`. Пробрасывает порт 8080 из контейнера наружу (на порт 30080), позволяя получить доступ к веб-интерфейсу через браузер хост-машины
* **ConfigMap**: `mentorflow-config` хранит неконфиденциальные конфигурационные данные (URL баз данных, профили Spring), передавая их в поды в виде переменных окружения
* **Secret**: `mentorflow-secret` безопасно хранит чувствительные данные (пароль пользователя Postgres, токен GitHub API), изолируя их от исходного кода манифестов

## 2. Механизм взаимодействия сервисов
Сервисы взаимодействуют между собой с помощью встроенного в Kubernetes механизма Service Discovery, который работает на базе CoreDNS:

* Приложению MentorFlow не нужно знать динамические и постоянно меняющиеся IP-адреса конкретных подов с базами данных
* Подключение происходит по статичным доменным именам сервисов, которые мы передали через ConfigMap. Например, Spring Boot стучится в PostgreSQL по адресу `jdbc:postgresql://postgres-service:5432/mentorflow_db` и в кэш по адресу `redis-service:6379`.
* Внутренний DNS-сервер кластера на лету разрешает эти имена в ClusterIP сервисов, а те, в свою очередь, автоматически маршрутизируют запросы на доступные и здоровые поды баз данных
